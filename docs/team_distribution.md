# Организация совместной разработки

Технические требования — в [архитектуре](architecture.md), задачи и статусы —
в [плане работ](work-plan.md). Правила агента — в [AGENTS.md](../AGENTS.md).
Владельцы, календарные сроки и распределение
по фиксированному числу участников пока не ведутся.

## Работа над задачей

1. Выбрать назначенный ID с выполненными зависимостями и прочитать требования.
2. Проверить `git status` и существующий код. Отметить `in_progress`.
3. Выполнить только эту задачу, сохраняя подходящие части реализации коллеги.
4. Проверить наблюдаемое поведение и записать фактические результаты в план.
5. Передать результат в `review`. После приёмки и интеграции в проект — `done`.

По умолчанию работа идёт последовательно. Коммиты и интеграцию выполняют
по отдельной команде. PR не обязателен для одиночной сессии.
При параллельных реализациях каждому агенту нужны собственные ветка/worktree
и непересекающаяся область файлов. SQL-схему, миграции, DTO, Compose и lockfiles
меняет один автор одновременно. Миграции нумеруются последовательно.
Worktree не изолирует контейнеры: тестовым БД, портам и Compose-проектам
задаются отдельные имена. Пользовательские данные не используются в тестах.

Изменение общих контрактов сначала отражается в архитектуре и зависимых задачах.
Архитектура не дублируется в локальных планах отдельных агентов.
Для поставленной задачи достаточно необходимых проверок; соседние улучшения,
новая инфраструктура и дополнительные форматы не добавляются попутно.

## Передача задачи агенту

Указать ID, относящиеся разделы архитектуры, область файлов, критерии результата,
способ проверки и разрешённые Git-действия.

Одна задача — один проверяемый результат. Крупную задачу можно разделить
на подзадачи с собственными критериями, сохранив исходный ID как общий пункт.
При передаче между сессиями записываются сделанное, непроверенное и следующий шаг.
Прогресс определяется работающими сценариями, а не количеством кода или коммитов.

Единственный источник статусов — `work-plan.md`. Дополнительная доска пока
не требуется. При последующем переносе в Issues старые ID сохраняются,
а в плане остаются ссылки; две независимые таблицы статусов не поддерживаются.

## Ревью и интеграция

1. Участник передаёт ID задачи, отчёт исполнителя и путь worktree либо ветку.
2. Ревьюер сверяет требования, границы задачи, код, staged/unstaged diff и
   отчёт. Тесты, сборки, сервисы и проектные скрипты ревьюер не запускает.
3. Замечания содержат конкретный дефект, его последствия и необходимое
   исправление. Непроверенные сценарии явно отделяются от обнаруженных ошибок.
   Недостающие проверки и исправления возвращаются исходному исполнителю.
4. Исполнитель исправляет результат и повторяет затронутые проверки.
   Ревьюер читает исправленный diff и отчёт; прежняя приёмка соседних задач
   не повторяется без новой причины или прямого запроса.
5. После приёмки участник коммитит и интегрирует результат либо явно поручает
   это исполнителю. Ревьюер даёт команды, учитывая фактическое состояние Git.
   Если основная ветка ушла вперёд, интеграция включает сохранение обеих сторон
   общих документов и проверку совместимости исполнителем.
6. После приёмки и интеграции задача становится `done`; затем выбираются
   следующие задачи по зависимостям. Наличие worktree не доказывает начало задачи,
   наличие коммита само по себе не доказывает её приёмку.

README не используется как отчёт об этапах. Инструкции разработки находятся
в `development.md`, прогресс и ограничения — в `work-plan.md`.
Промпты выдаются только в чате. Хеши коммитов проекта в документацию не вносятся.

## Обновление веток задач

Обычный порядок интеграции: коммит результата в собственной ветке задачи →
`git rebase <основная-ветка>` в её worktree → проверка результата исполнителем →
`git merge --ff-only <ветка-задачи>` в основной ветке. Обновление через rebase
выполняется по явному поручению на интеграцию; само наличие этого правила
не разрешает агенту коммитить или переписывать историю.

Перед rebase рабочее дерево и индекс должны быть чистыми. Незакоммиченные
изменения не прятать и не удалять автоматически. Конфликты разрешать с сохранением
обеих сторон требований и отчётов; документы целиком через ours/theirs не выбирать.
После rebase проверить итоговый diff и выполнить затронутые проверки.
Если изменена только документация, полный прогон backend не требуется.

Rebase применяется к собственной ветке задачи, на коммиты которой не опираются
другие участники. Общую ветку и уже интегрированную историю не переписывать.
Если веткой пользуются другие участники, сначала согласовать способ обновления;
обычный merge остаётся допустимым исключением. Force-push без отдельного поручения
не выполнять. Прежние merge-коммиты специально не удалять.
