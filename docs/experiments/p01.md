# P01 — локальная LLM по HTTP

Статус: `done`. P01 и завершающий рефакторинг приняты пользователем.
Результат интегрирован в `mvp`.

Эксперимент выполняется 2026-11-13 на MacBook Pro, Apple M4 Pro,
Mac16,7, arm64, 48 GiB (51 539 607 552 байта), macOS 26.7.2 (25G332).
Это отдельный proof of concept без изменений приложения.

## Выбранный профиль и официальные источники

До установки проверены PATH, `/Applications`, стандартные каталоги
`~/.ollama/models`, `~/.cache/huggingface/hub`, `~/.lmstudio/models`,
процессы LLM и TCP listeners. Подходящих установленных runtime/весов не найдено.
Использован имеющийся Homebrew Python 3.13.18; системный Python 3.9.6 не выбран.

Выбран один профиль: Ollama **0.40.16**, официальный macOS CLI-архив
`ollama-darwin.tgz` (186 116 182 байта), **qwen3:8b**, 8.19B, **Q4_K_M**,
около **5.2 GB** весов. Для коротких проверок установлен контекст 8192 токена,
одна параллельная генерация, одна загруженная модель, keep-alive 10 минут.
Streaming выключен; temperature=0, seed=42, max_tokens=512,
`reasoning_effort="none"`. Последняя настройка отключает thinking этого профиля;
она не является универсальным требованием к будущему клиенту приложения.

## Повторение после переноса общей установки

Общий Ollama отделён от P01: runtime, архив, модели и логи хранятся в
игнорируемом `local/ollama/`; общие shell-скрипты — в `scripts/models/`.
В `experiments/p01/` остаются только конфигурация клиента, зависимости,
проверки, исходный manifest и evidence. Старые результаты сохранены без изменений.

Команды выполняются из корня репозитория в обычном терминале macOS:

```sh
sh scripts/models/setup.sh
PYTHON=/opt/homebrew/bin/python3.13 sh experiments/p01/setup-client.sh
```

Общий setup проверяет файлы Ollama 0.40.16 по `scripts/models/runtime.sha256`.
Корректная существующая установка пропускается **без сети и распаковки**.
Если runtime повреждён или отсутствует, сначала используется уже скачанный
архив `local/ollama/ollama-darwin.tgz` с проверкой SHA-256. Только при отсутствии
корректного архива setup скачивает фиксированный релиз. Веса setup не загружает.
`setup-client.sh` готовит только отдельный Python venv P01 и зависимости с
точными версиями из `requirements.txt`; существующий venv переиспользуется.

Параметры общего setup/serve задаются переменными окружения:

| Переменная | По умолчанию |
|---|---|
| `OLLAMA_RUNTIME_DIR` | `<repo>/local/ollama/runtime` |
| `OLLAMA_MODELS` | `<repo>/local/ollama/models` |
| `OLLAMA_LOG_DIR` | `<repo>/local/ollama/logs` |
| `OLLAMA_HOST` | `127.0.0.1:11435` |

Абсолютные пути используются непосредственно, относительные считаются от корня
проекта независимо от cwd. `OLLAMA_HOST` задаётся как `host:port`, без схемы;
допустимы только `127.0.0.1`, `localhost` и `[::1]`, порт 1–65535.
Для общей установки вне каталога проекта задать одинаковые пути в setup/serve;
если это путь внутри Git-репозитория, отдельно исключить его из Git.
Пример альтернативного адреса: `export OLLAMA_HOST=127.0.0.1:11436`.
Установка может переиспользоваться следующими экспериментами без копирования.

В терминале A:

```sh
sh scripts/models/serve.sh
```

Скрипт проверяет занятость выбранного TCP-порта до запуска, отказывается
запускаться при занятом порте и не завершает чужие процессы. Сервер работает
на переднем плане; остановка — Ctrl-C в этом терминале. Логи дописываются в
`$OLLAMA_LOG_DIR/server.log`. Контекст 8192, одна параллельная генерация,
одна загруженная модель, keep-alive 10 минут, `OLLAMA_NO_CLOUD=1` сохранены.
Нет автозапуска, системного сервиса или GUI.

В терминале B задать **тот же** `OLLAMA_HOST`, если в A он переопределён:

```sh
export OLLAMA_HOST=127.0.0.1:11435
curl --noproxy '*' --fail "http://$OLLAMA_HOST/api/version"
# Для стандартного пути; при переопределении использовать выбранный OLLAMA_MODELS.
echo 'b3d9ba7c899cfd112df2574c6a91458a70b724c5e4e50dfffd75574b2d1648e7  local/ollama/models/manifests/registry.ollama.ai/library/qwen3/8b' | shasum -a 256 -c -
. experiments/p01/config.example.sh
mkdir -p experiments/p01/.local/results
PYTHON=experiments/p01/.venv/bin/python sh experiments/p01/curl-russian.sh \
  > experiments/p01/.local/results/curl-first.txt
experiments/p01/.venv/bin/python experiments/p01/probe.py \
  --output experiments/p01/.local/results/first.json
```

`BASE_URL`, `MODEL`, `API_KEY` настраиваются независимо; пример сохраняет уже
заданные значения. Если `BASE_URL` отсутствует, он выводится из `OLLAMA_HOST`
с добавлением `http://` и `/v1`. При изменении адреса в текущем shell заново
задать `BASE_URL` либо выполнить `unset BASE_URL` перед source примера.
Значение API_KEY `local-p01` — публичная заглушка, локальный Ollama его игнорирует.
Настоящие секреты хранить в локальном окружении, не в отслеживаемом примере.

На этой машине модель уже перенесена; **повторный pull не требуется**.
Только для новой машины без весов, при работающем своём сервере:

```sh
OLLAMA_HOST=127.0.0.1:11435 local/ollama/runtime/ollama pull qwen3:8b
```

При нестандартном runtime использовать `$OLLAMA_RUNTIME_DIR/ollama`.
Для чистой установки нужен доступ к GitHub, registry Ollama и PyPI;
в среде Codex сеть, Metal и loopback потребовали разрешений вне sandbox.
Тег модели может измениться: при несовпадении manifest остановить проверку;
другая ревизия не считается повторением. Ollama при pull проверяет хеши слоёв.
При первом запуске также создаются локальные ключи `~/.ollama/id_ed25519*`,
которые в Git не попадают. Вход в облако не нужен.

Затем остановить **свой** сервер Ctrl-C в A, убедиться, что порт освободился,
повторить запуск и в B выполнить curl и probe с другими именами результатов:

```sh
PYTHON=experiments/p01/.venv/bin/python sh experiments/p01/curl-russian.sh \
  > experiments/p01/.local/results/curl-second.txt
experiments/p01/.venv/bin/python experiments/p01/probe.py \
  --output experiments/p01/.local/results/second.json
```

Curl должен вернуть содержательный русский ответ, HTTP 200 и время.
Python завершается с кодом 0 только после всех трёх сценариев, иначе сохраняет
ошибку в evidence и завершается ненулевым кодом. Authorization header не пишется.
Для собственных материалов использовать только игнорируемые пути результатов;
отслеживаемые evidence содержат исключительно встроенные вымышленные заметки.

После окончательного Ctrl-C отсутствие listener проверить
`lsof -nP -iTCP:11435 -sTCP:LISTEN` (или свой порт): код 1 без вывода означает,
что listener отсутствует. Не использовать `killall` или общий поиск PID.
Проверка исключений Git для стандартной установки:

```sh
git check-ignore local/ollama/runtime/ollama local/ollama/models/blobs/* local/ollama/logs/server.log
git ls-files -- local/ollama/
```

Первая команда перечисляет игнорируемые файлы, вторая должна быть пустой.

## Что именно проверяет Python

1. Реальный нестриминговый POST `/v1/chat/completions`, русский ответ.
2. Отдельный диалог с `tools`: разрешена только `search_notes(query: str)`.
   Это поиск подстроки по двум встроенным заметкам без сети, файлов, SQL и eval.
   Имя, тип вызова, ID и JSON-аргументы проверяются до исполнения; Pydantic
   запрещает лишние поля и неверные типы, ограничивает длину и пустой query.
   Наличие `message.tool_calls` обязательно; текстовая имитация вызова — ошибка.
   Результат отправляется как `role=tool` с `tool_call_id`, затем проверяется
   финальный русский ответ с датой, временем и макетом. Максимум **четыре запроса
   к модели во всём tool-диалоге**, без скрытых повторов HTTP; не более четырёх
   вызовов функции в одном ответе. Скрипт падает при неизвестном инструменте.
3. Отдельный POST с **`response_format={"type":"json_object"}`** без tools.
   `Enrichment.model_validate_json` проверяет `summary: str`, `tags: list[str]`,
   обязательность и непустоту полей, строгие типы и отсутствие лишних полей.
   JSON Schema в API для этого запроса не передаётся.

Полные запросы, HTTP status, ответы и секунды сохраняются в JSON evidence.
API `/api/version`, `/api/show` и `/api/ps` используются только для метаданных
runtime/модели/памяти, а не вместо проверок `/v1/chat/completions`.

Это wall-clock время единичных запросов; OS file cache не очищался.

Русский ответ curl и Python в обоих прогонах:

> Резервные копии заметок помогают сохранить важную информацию в случае потери
> данных или сбоя устройства. Они обеспечивают возможность восстановить заметки
> в любой момент, не потеряв важные данные.

В первом tool-ответе `content=""`, `finish_reason="tool_calls"`, а структура
именно `choices[0].message.tool_calls`:

```json
[{"id":"call_69i4qtp2","index":0,"type":"function","function":{"name":"search_notes","arguments":"{\"query\":\"Орбита\"}"}}]
```

Следующий запрос содержит исходный assistant tool call и
`{"role":"tool","tool_call_id":"call_69i4qtp2","content":"..."}` с найденной
заметкой. Финальный ответ в обоих прогонах:

> Встреча по проекту Орбита состоится 15 мая в 10:00. Нужно подготовить макет.

Для tool-диалога понадобилось два запроса из разрешённых четырёх.
Во втором прогоне получен новый native call ID `call_aw0fosck`.

Отдельный JSON mode в обоих прогонах вернул и прошёл строгую проверку Pydantic:

```json
{
  "summary": "Встреча по учебному проекту состоится 15 мая. Нужно подготовить макет.",
  "tags": ["учебный проект", "встреча", "макет", "дата"]

```

Проверка типов не подменяет оценку содержания: здесь summary вручную сверено
с вымышленным входным текстом. При этом tags свободно выбраны моделью.

### Память и окружение

До загрузки весов: `memory_pressure` сообщил 48 GiB и system-wide memory free
86%; `vm.swapusage`: total/used/free=0; `df -h .`: доступно 329 GiB.
Метрика free из `memory_pressure` не равна объёму свободных физических страниц.
Сервер обнаружил Metal Apple M4 Pro, доступный ему GPU budget 37.4 GiB.

После запросов оба `/api/ps` сообщают `size=size_vram=5 801 708 093` байта
(около 5.40 GiB), runner=`llamacpp`, context_length=8192, Q4_K_M.
System-wide memory free в обоих снимках 73%; swap total/used/free=0,
swapins/swapouts=0. После второго прогона RSS llama-server — 6 531 008 KiB
(около 6.23 GiB), управляющего Ollama — 34 672 KiB. Последние строки файлов
memory имеют формат `PID PPID RSS_KiB process`; первый снимок включает RSS
только управляющего процесса. RSS и Metal allocation описывают пересекающуюся
unified memory, складывать их нельзя. Это снимки после запросов, **точный пик
памяти за весь запуск не измерен**. Другие приложения Mac продолжали работать.
Локальные артефакты заняли около 5.6 GiB, venv — 21 MiB (`du -sh`).

Исторические команды получения снимков до переноса:

```sh

curl --noproxy '*' -fsS http://127.0.0.1:11435/api/show \
  -H 'Content-Type: application/json' -d '{"model":"qwen3:8b"}'

sysctl -n vm.swapusage
ps -axo pid,ppid,rss,comm | awk '$4 ~ /p01\/\.local\/runtime\/(ollama|llama-server)/ {n=split($4,a,"/"); print $1, $2, $3, a[n]}'
```

В `model-metadata.json` из `/api/show` оставлены details, model_info,
capabilities и параметры; большой текст лицензии и шаблона не дублируется.
Метаданные содержат точное число параметров 8 190 735 360 и исходный
максимальный контекст 40960; фактический контекст сервера ограничен 8192.

### Дополнительные проверки и ограничения

До переноса выполнены с кодом 0 (старые setup/serve теперь перенесены):

```sh
experiments/p01/.venv/bin/python -m py_compile experiments/p01/probe.py
sh -n experiments/p01/setup.sh experiments/p01/serve.sh experiments/p01/curl-russian.sh
experiments/p01/.venv/bin/python -m pip check

```

Локально также проверено отклонение query неправильного типа, лишнего поля
и строки из пробелов; summary неправильного типа, tags с числом и отсутствующего
tags. Эти проверки валидаторов не засчитывались как доказательство API.

Реальных блокировок P01 не осталось. Проверен только выбранный профиль на
двух вымышленных заметках, не общее качество русского языка или устойчивость
агента к произвольным запросам. При фиксированном seed полная идентичность
ответов на другом runtime/железе не гарантируется. Streaming, принудительная
JSON Schema, одновременные JSON mode + tools и нагрузка не исследовались.
Другие модельные адаптеры, ASR, embeddings, PostgreSQL, RAG и приложение
не проверялись и не изменялись. Серверы эксперимента остановлены; веса, runtime,
venv и локальные ключи сохранены для повторения вне Git. После приёмки и
интеграции результата задача переведена в `done`.
