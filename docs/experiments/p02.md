## Выбранный профиль

Выбрана компактная многоязычная embedding-модель для локального Apple M4 Pro
48 GB. Официальная [карточка Qwen](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)
описывает 1024 измерения, инструкцию для запросов и отсутствие инструкции для
документов. Артефакт взят из [Ollama library](https://ollama.com/library/qwen3-embedding:0.6b).
Проверялась одна модель, сравнение кандидатов не проводилось.

- Runtime: общий Ollama 0.40.16, native Metal/llamacpp, macOS 26.7.2 arm64.
- Модель: `qwen3-embedding:0.6b`, 595.78M параметров, GGUF Q8_0.
- Размерность: 1024, без усечения; `num_ctx=8192`, `truncate=false`, `keep_alive=10m`.
- `/api/embed`: настоящий пакет из 24 документов, затем отдельный HTTP-запрос
  для каждого поискового запроса. Нет mock и fallback.
- Нормализация векторов: явная L2 в Python, проверка длины, конечности и
  ненулевой нормы; PostgreSQL хранит float32 `vector(1024)`.
- Метрика: cosine distance `<=>`, score = `1 - distance`; top-3 с устойчивым
  вторичным порядком по ID. Score не является вероятностью релевантности.

Query instruction (одинаковая для RU/EN), полный формат входа:

```text
Instruct: Given a web search query, retrieve relevant passages that answer the query
Query: {нормализованный запрос}
```

Документам instruction не добавляется. Никакой скрытой инструкции сервера
runner не задаёт. Исходные нормы от Ollama измерены, затем клиент повторно
нормализует векторы. Поведение HTTP API сверено с
[официальной документацией](https://docs.ollama.com/api/embed).

Digest Ollama: `ac6da0dfba84a81fdbfbaf330198c33cd77c4cdfc53e8bc50eb581914a15621d`.
SHA-256 слоя весов: `06507c7b42688469c4e7298b0a1e16deff06caf291cf0a5b278c308249c3e439`,
639,150,592 байт. Контрольная сумма локального слоя реально
вычислена и совпала с manifest; метаданные сохранены в
[model-manifest.json](../../experiments/p02/model-manifest.json).
Runner отклоняет подмену тега другим digest.

Runtime и веса расположены только в общем `local/ollama/`, не в эксперименте.
Переиспользуются `scripts/models/setup.sh` и `serve.sh`; общий setup проверил
уже установленный runtime и пропустил скачивание. Загружены только новые
embedding-веса. Модель генерации P01 не загружалась для этого эксперимента.

Python 3.13.18, Psycopg 3.2.13; зависимости фиксированы в
`experiments/p02/requirements.txt`. ORM и pgvector-python не нужны: сериализация
вектора передаётся как связанное значение `%s::vector` через Psycopg 3.
PostgreSQL 17.8 / pgvector 0.8.1, linux/arm64; Docker client 29.9.3,
server 29.2.1, Compose 5.7.0. Образ зафиксирован по версии и digest в Compose.

## Изоляция и SQL

Compose-проект `local-note-p02`, контейнер `local-note-p02-db-1`, отдельный
volume `local-note-p02_p02-data`, endpoint `127.0.0.1:55432`, БД и роль
`p02_experiment`. Пароль в Compose — публичная константа только для этой
одноразовой тестовой БД. Пользовательская БД не использовалась.
Root Compose и backend не менялись.

Runner имеет фиксированный тестовый DSN и не читает DATABASE_URL или .env.
Проверяет имя БД и роль, применяет экспериментальную
[001_initial.sql](../../experiments/p02/001_initial.sql) и заменяет содержимое
только своей таблицы `p02_notes`. `--reuse` ничего не пересоздаёт.
Модельные вызовы выполняются вне транзакций: документы вычислены до подключения,
при запросах используется autocommit. Запись корпуса — одна короткая транзакция.

```sql
SELECT id, title, 1 - (embedding <=> %s::vector) AS score
FROM p02_notes
ORDER BY embedding <=> %s::vector, id
LIMIT %s;
```

Все значения и limit связаны параметрами. `EXPLAIN (ANALYZE, BUFFERS)` реально
выполнен: Seq Scan по 24 строкам, top-N heapsort, 25 kB, Execution Time 0.074 ms
в первом прогоне. ANN-индекс на таком корпусе не создаётся; это точный dense
retrieval. Полный план находится в JSON evidence. Для каждого запроса порядок
SQL top-3 совпал с независимым cosine-расчётом Python по сохранённым векторам.
Неверная размерность `[1,0]` отвергнута PostgreSQL: SQLSTATE 22000,
`different vector dimensions 1024 and 2`; соединение после ошибки пригодно
для последующих запросов.

Сохранены и прочитаны обратно 24 вектора длины 1024; нормы после хранения:
0.9999999846…1.0000000092.
Исходные нормы документов от endpoint:
0.9999994999…1.0000003216.
Проверены также ID, язык, заголовок, текст и digest всех строк.

## Воспроизведение и реальные проверки

Из корня репозитория, зависимости клиента требуют Python 3.13:

```sh
sh scripts/models/setup.sh
PYTHON=/opt/homebrew/bin/python3.13 sh experiments/p02/setup-client.sh
# В отдельном терминале (оставить работающим):
sh scripts/models/serve.sh
```

Далее в другом терминале:

```sh
OLLAMA_HOST=127.0.0.1:11435 local/ollama/runtime/ollama pull qwen3-embedding:0.6b
docker compose -f experiments/p02/compose.yaml up -d --wait
experiments/p02/.venv/bin/python experiments/p02/run.py --output experiments/p02/results/new-run.json
# Проверка уже сохранённого корпуса без вычисления документов заново:
docker compose -f experiments/p02/compose.yaml restart db
docker compose -f experiments/p02/compose.yaml up -d --wait
experiments/p02/.venv/bin/python experiments/p02/run.py --reuse --output experiments/p02/results/new-restart.json
```

Существующие evidence не перезаписываются; выбирать новые имена. При смене
артефакта тега runner завершится ошибкой pin: для повторения нужен прежний
слой весов из общего кэша. DSN намеренно нельзя направить в пользовательскую БД.
Для свежего запуска runner заменяет данные только `p02_notes` тестовой БД.

Реально выполнены команды выше с output `eval-first.json` и
`after-db-restart.json`: оба кода 0. После pin-проверки модели выполнен ещё
`--reuse --output experiments/p02/results/pinned-recheck.json`: код 0.
При перезапуске Compose также пересоздал контейнер из-за фиксации digest
образа; данные сохранены в том же отдельном volume. Документы повторно не
вычислялись; выдача всех 20 запросов совпала по порядку ID.

Первый запуск без доступа к loopback завершился кодом 1 до HTTP-запроса:
`URLError: Operation not permitted`; он сохранён отдельно как
[sandbox-denied.json](../../experiments/p02/results/sandbox-denied.json),
не считается модельным прогоном. Доступ к Docker, запуск Ollama и загрузка
Psycopg также потребовали выполнения за пределами sandbox; после разрешения
реальные запросы прошли. Других runtime/SQL ошибок в eval не было, кроме
намеренной проверки неправильной размерности.

Дополнительно реально выполнены с успешным результатом:

```sh
experiments/p02/.venv/bin/python -m py_compile experiments/p02/run.py
sh -n experiments/p02/setup-client.sh
experiments/p02/.venv/bin/python -m pip check
docker compose -f experiments/p02/compose.yaml config --quiet
docker image inspect pgvector/pgvector:0.8.1-pg17 --format '{json .RepoDigests}'
git diff --check
```

SHA-256 весов проверен отдельным Python-вызовом hashlib по файлу из общего
кэша. Корпус и запросы проверяются по SHA-256 при каждом запуске runner.
Веса, runtime и venv игнорируются Git. SQL-проверки выполнены на настоящем
pgvector, mock-адаптеры в этом эксперименте не использовались.

Блокировок P02 нет. Проверены только короткие синтетические тексты, один
профиль модели и точный cosine-поиск. Непроверены длинные документы, ANN,
гибридный retrieval, большой корпус и качество за пределами набора.
Готовность следующих задач и интеграции backend из этого результата не следует.
Коммиты не создавались. После проверки тестовый контейнер и поднятый для P02
Ollama остановлены; volume с 24 векторами и общий кэш модели сохранены локально.
