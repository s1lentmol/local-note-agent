# Работа кодинговых агентов

## Источники требований

- `docs/architecture.md` — актуальная архитектура и контракты.
- `docs/work-plan.md` — задачи, зависимости, приёмка и состояние реализации.
- `docs/team_distribution.md` — порядок совместной работы и интеграции.
- `docs/agent_plan.md` — историческое описание, не источник технических решений.
- `docs/development.md` — команды установки, запуска и проверок

Перед изменениями прочитать относящиеся к задаче разделы и проверить `git status`.
Не перезаписывать чужие или не относящиеся к задаче изменения.

## Роли

- **Исполнитель** реализует назначенную задачу, запускает необходимые проверки,
  сохраняет фактические результаты и передаёт работу в `review`.
- **Архитектор / планировщик / ревьюер** читает требования, код, Git diff,
  staged/unstaged изменения и отчёты исполнителей. В этом режиме не запускает
  тесты, lint, сборки, сервисы, миграции, модельные вызовы и установку зависимостей.
  Не запускает проектные скрипты, включая проверочные. Недостающую проверку
  поручает исполнителю. Не объявляет чужие результаты собственным запуском.
  Прямое поручение на актуализацию планов разрешает правки документации,
  но не реализацию или самостоятельное выполнение проверок.

Отдельные проверки ревьюер выполняет только по явной новой команде участника;
обычный запрос «проверь работу агента» означает чтение кода, diff и отчёта.

## Границы задачи

Работать над назначенным ID и в согласованной области. Если ID не указан,
выполнять прямой запрос участника; не выбирать дополнительную задачу самостоятельно.
Не реализовывать соседние пункты плана и не менять стек попутно.

При реализации задачи обновлять её запись в плане: состояние,
блокировку и результаты проверок. Не выдумывать владельца, ссылки или выполненные
проверки. `done` означает, что изменения слиты и приёмка выполнена;
подготовленный результат передаётся в `review`.
При прямом запросе только на обсуждение или ревью код и статусы не менять.

Параллельные реализации выполняются в разных ветках и worktree.
Не выполнять разрушительные Git-команды, не редактировать чужие ветки.
Изменения общих контрактов, миграций и зависимостей должны входить в назначенную
задачу. При необходимом расширении описать зависимость и согласовать границы.

## Свойства реализации

- PostgreSQL и pgvector — единое хранилище данных и поискового индекса.
- Доступ к БД — явный параметризованный SQL через Psycopg 3, без ORM;
  изменения схемы — нумерованные SQL-миграции.
- Переиспользовать подходящие Storage, extractors, проверки и тестовые сценарии
  существующего прототипа. Сохранять рабочий способ запуска старой реализации
  до замены соответствующей функциональности. Старые SQLite/ORM/API версий
  можно заменить при реализации и проверке нового варианта.
- В MVP один worker и один последовательный `process` job для индекса и обогащения.
  Отдельные index/enrich очереди, backoff и масштабирование не добавляются.
- Цитаты, список источников ответа, locators, выделение утверждений,
  сегменты и таймкоды аудио не входят в MVP. Внутренние chunks для поиска допустимы.
- ASR возвращает полный текст и язык. Обязательны голосовые Telegram OGG/Opus,
  WAV и MP3, проверенные декодером; старый whitelist не должен блокировать OGG.
- PDF/OCR/HTML — дополнительные задачи, не условие готовности основного MVP.
- API, Telegram и инструменты диалога используют общий прикладной слой.
- Генерация, embeddings и ASR имеют отдельные заменяемые адаптеры.
- Модельные вычисления и извлечение файлов выполняются вне транзакций БД.
- Изменение заметки удаляет её прежние производные данные и запускает обработку;
  история редакций и счётчики версий не добавляются.
- Отменённый job и job с устаревшей lease не могут публиковать результат.
- Не добавлять незаявленные форматы, авторизацию, сервисы и инфраструктуру.
- Не сохранять ключи, `.env`, пользовательские материалы и веса моделей в Git.

## Проверка и передача результата

Исполнителю выполнять проверки, соответствующие изменению. Для SQL, блокировок и векторного
поиска использовать тестовый PostgreSQL с pgvector. Детерминированные проверки
модельных сценариев используют тестовые адаптеры; реальные endpoint проверяются
отдельным smoke/eval запуском. Не объявлять такой запуск выполненным без доступа.

В отчёте указать изменённое поведение, выполненные команды и их результаты,
непроверенные части и оставшиеся блокировки. Успех отдельного модуля не означает
готовность интеграционного этапа.

## Документация и Git

- README — назначение проекта, краткое описание, быстрый старт и ссылки.
  Прогресс, отчёты, временные ограничения и результаты проверок — в `work-plan.md`;
  технические инструкции — в `development.md`.
- Промпты передаются в чате, не сохраняются в файлы репозитория.
- Хеши коммитов проекта в документации не ведутся. Версии и checksum внешних
  моделей, runtime и зависимостей сохраняются для воспроизводимости.
- Не закреплять конкретное имя рабочей ветки как требование проекта.
- Коммиты, слияния, rebase и удаление worktree выполняются только по прямой
  команде; для интеграции ревьюер по умолчанию даёт участнику команды.
